---
title: "What let me build a game overnight"
description: "The reason Claude could build a working kids' game in one night wasn't speed, it was that the project was shaped so it could check its own work."
date: 2026-09-08
---

I got sick enough of kids' games loaded with video ads and paywalls that I decided to just build one myself, and with Claude doing the typing, I did it in one night, for my kid. I kept adding and fixing things while watching her play the next morning, but there was something decently playable waiting for her when she woke up. The part I actually want to talk about isn't the "one night" part, because that makes it sound like the AI just writes code fast. What actually let that happen is that the project was set up so the AI could check its own work without me standing over it or a phone in the loop, and I think that's the reusable part.

There are four pieces to it, and none of them are exotic.

**Split the game out from the phone.** The game (it's a rhythm game, tap along with a bee hopping flower to flower on the beat) is built as two Gradle modules, which is just Android's way of saying "two separate chunks of code that get built together." One module, `:core`, holds the actual game: the notes, the timing, the judge that decides whether your tap landed on the beat, the scoring, the progression, the shop. It's plain Kotlin with nothing Android-specific in it at all. The other module, `:app`, is a thin shell built with Compose, Android's UI toolkit, that just draws the flowers and plays the sounds and hands taps to `:core` to grade. `:app` doesn't decide anything, it just shows what `:core` already decided.

**The rule that keeps that split real is a test, not a habit.** A convention like "core doesn't touch Android" stops being true in about a week if nothing enforces it, especially when an agent is the one writing the code and it's just trying to get the feature working. So `:core` is only allowed to import `kotlin.*`, nothing else: no `java.*`, no `android.*`, no reading the system clock directly, no threads. Time gets passed in by whoever's calling, randomness is seeded so a run is reproducible, and saving a game is just producing a string that the phone writes down somewhere. There's a test called `PortabilityTest` that scans every file in `:core` and fails the build if any of that sneaks in. Nobody has to remember the rule, the build just won't pass if it's broken.

That split is what makes checking the work cheap. `./gradlew :core:test` runs the entire rules suite, 157 tests as of the last run, in seconds, on any machine with a JDK. No Android SDK, no emulator, no phone. That's the whole reason an agent working overnight, with nobody around to hand it a device, could still know whether the scoring formula or the timing judge was actually right. The same shape shows up in an earlier phone game I built the same way, a party game that plays like Heads Up but with songs from your own Spotify playlists: the no-repeat shuffle, the tilt-gesture logic, and the part that finds a song's chorus were all pulled out as plain logic with their own unit tests, and they were all correct the first time they ran on a real device. That's the whole pitch for doing this: pure logic is the part you can actually be sure about, so it's worth putting as much of the game into it as you can stand.

The last piece is being honest about what "tested" even means, because an agent will tell you something is done whether it is or not. The status doc for this game keeps "code written," "compiles," "unit tests passing," and "verified on a real device" as four separate rows instead of collapsing them into one checkmark, and the test-coverage doc distinguishes a row that's actually "Covered" from one that's "Written, not yet verified" because it ran in a sandbox with no device to confirm it on. That sounds like process for its own sake, but it's really just refusing to let "the tests pass" quietly become "it works," which are not the same claim, especially the morning after an AI has been up all night telling you everything's fine.

Two smaller habits carried their weight too, worth a sentence each. Before any of the Android code existed, the whole feel of the game got prototyped as a single HTML file you could just open in a browser and tap around in, because a screenshot can't tell you whether a rhythm game feels fair, you have to actually play it. And the timing offset that makes tapping feel right wasn't guessed at, the app logs every tap's timing error to a file on the phone, I pull it off with adb, and a small script crunches it into medians and percentages. That's how I landed on the specific millisecond offset that's baked in now, not a number I picked because it felt about right.

None of this is complicated on its own, splitting logic from UI and writing tests for it is old advice. What's different about doing it with an agent is that the payoff shows up immediately instead of eventually, because the agent is the one running the loop of change, test, check, repeat, all night, and it can only do that loop honestly if there's something fast and pure it can actually run. I keep wondering what else I've built where the slow part was never the code, it was always the checking.
